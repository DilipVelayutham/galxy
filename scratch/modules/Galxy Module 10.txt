1. Scope
This module gives Asil control over everything on the site that isn't a category, product, order, or review — the homepage hero, about page, footer, contact details, SEO metadata, and general-purpose media uploads. Its entire reason for existing is the project's core promise: Asil should never need a developer to update copy, swap a banner image, or change the contact number.
This module also owns the shared Cloudinary upload utility that other modules have been flagged throughout this spec to consolidate around, since general media handling belongs here rather than being duplicated per-module.

4. API Contract
Standard response shapes as established in prior modules.
4.1 Public Routes
GET /api/site-content/:section
Success 200: { "success": true, "data": { "section","content" } }
Errors: 404 — unknown section, or content not yet seeded
 
Recommended: seed all 6 sections with sensible defaults at project setup
so this route never legitimately 404s in production — an empty/missing
hero section would break the homepage.

Optionally, add a bulk convenience route to save the frontend multiple round-trips on initial homepage load:
GET /api/site-content?sections=hero,footer,social_links
Success 200: { "success": true, "data": { "hero":{...}, "footer":{...}, "social_links":{...} } }

4.2 Admin Routes (require @require_admin)
GET /api/admin/site-content/:section
Same as public but no restrictions on which sections are visible (public
route could later restrict certain sections from ever being public-facing
if new internal-only sections are added — not needed for the current 6).

PUT /api/admin/site-content/:section
Body: { "content": {...} }
- Validates the incoming content{} shape against that section's expected
  schema (content_schema_validator) — reject with 400 + field errors on
  mismatch, don't let malformed content reach the live site and break
  the homepage rendering.
- Full replace of the content object, not a deep patch — simplest
  contract for the admin CMS forms to reason about (each section has its
  own dedicated admin form matching its known shape).
Success 200: { "success": true, "message": "Content updated", "data": {...} }

6. Content Validation Rules
content_schema_validator checks that the submitted content object for a given section contains only expected keys with correct types (string fields aren't objects, URLs are plausible URLs, etc.) — mirrors the spirit of Module 2's attribute_schema validator, but against a fixed set of known section shapes rather than a dynamic schema.
Rich text fields (about.body_text) should have a reasonable max length enforced server-side (e.g. 5,000 characters) to prevent runaway content breaking page layout.
URL fields (cta_link, social links, map_embed_url) should be validated as well-formed URLs before saving, to avoid silently broken links on the live site.

7. What This Module Does NOT Do
Does not manage category or product images beyond providing the shared upload utility they call into — the actual product.images / category.cover_image fields are written by Modules 2 and 3 respectively, using this module's media_upload_service.
Does not manage AI-generated images (Module 5 calls the shared uploader directly, uploading to its own galxy/ai-previews folder).
Does not manage review images (Module 9 calls the shared uploader, uploading to galxy/reviews).
Does not handle SEO for individual product/category pages — seo_home covers only the homepage; if per-product/per-category SEO metadata is needed later, that likely belongs as fields directly on those documents (Modules 2/3), not centralized here — flag as a future scope question, not building it in v1 unless requested.

8. Handoff Contract for Other Teams
Treat as frozen from Day 1:

Contract Item
Detail
Shared upload function
media_upload_service.upload_to_folder(file, folder_name) — the single upload function every other module should call for any Cloudinary upload need. Returns a plain URL string, ready to store directly on whatever document needs it.
Content fetch
GET /api/site-content/:section — used by the frontend to hydrate homepage hero, footer, contact info, and social links; frontend should never hardcode this content, always fetch it, so Asil's edits go live immediately without a redeploy (this is the module's entire reason for existing — treat any hardcoded content that bypasses this as a bug).
Fixed section enum
All six section values (hero, about, footer, contact, seo_home, social_links) are fixed enum values for v1 — if a new content section is needed later (e.g. a dedicated FAQ section), it should be added here as a seventh known shape, not bolted onto an existing section's content object.
