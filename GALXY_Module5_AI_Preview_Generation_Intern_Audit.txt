This audit compares the submitted branch (feat/m5-t1-core-prompt) against the Module 5 — AI Preview Generation specification document. 5. What's Missing vs. the Spec
PUT /api/admin/categories/:id/ai-prompt-template — correctly out of scope per the spec's own recommendation that Module 2 owns it; needs a confirmation handshake with that team, not code here.
No dedicated ai_cache_service.store_cache() implementation — currently relies implicitly on the ai_generations log doubling as the cache source of truth. Works, but should be documented as the intended design rather than left as a dead stub.
No automated test covers the Cloudinary upload failure path (i.e., nothing asserts what happens when cloudinary.uploader.upload() throws) — which is exactly the path where the mock-fallback bug above lives. Adding that test would have caught it.
No explicit test for AI_GENERATION_TIMEOUT_SECONDS actually cutting off a slow provider call (the requests timeout is wired up, but there's no test simulating a hang to confirm the 504 path end-to-end).
README.md is a single line (just the module name) — no setup, env var, or local-run instructions for the next developer, despite the config/env surface being fairly large (7+ env vars).
6. Strengths — What's Done Well
Worth calling out explicitly, since a review that's all gaps undersells genuinely solid work here:
Clean adapter pattern for the AI provider (AIProviderAdapter → GeminiProviderAdapter / MockProviderAdapter) exactly matches the spec's requirement to keep AI_PROVIDER genuinely swappable without a rewrite.
Generation flow in ai_service.py follows the spec's 8-step sequence precisely: validate → rate-limit → cache → build prompt → call provider (with timeout) → upload → log → respond — including returning 400 before ever touching the provider on invalid input.
Prompt builder correctly implements every rule from Section 5 of the spec: option-code-to-label resolution, affects_ai_preview exclusion, empty-placeholder cleanup with punctuation tidy-up, and a genuinely thoughtful custom_text sanitizer (HTML stripping, repeated-punctuation collapsing, and a real regex list of prompt-injection phrases), not just a token gesture at the requirement.
Caching correctly refuses to reuse a cached result whenever custom_text is present, matching the spec's explicit "never cache across different custom_text values" rule, and cache hits are logged with generation_time_ms: 0 and excluded from rate-limit counts exactly as specified.
Rate limiting correctly implements both tiers (per-session ceiling for guests, per-user daily ceiling for logged-in users) and correctly excludes cached hits from the count, per Section 8.
Error handling never leaks raw provider error text to the client — ai_provider_client failures are logged internally with full detail but the client only ever sees a generic message, and timeout vs. generic failure are correctly mapped to 504 vs. 502.
Admin auth test (test_compliance.py) explicitly tests and rejects loose-substring tokens and query-param bypass attempts, which shows real security awareness rather than a token happy-path test only.
MongoDB indexes on user_id, session_id, category_id, and created_at are created exactly as specified in Section 2.1, supporting the documented access patterns (history lookups, guest rate limiting, admin analytics, cleanup jobs).
7. Test Suite Verification
All 5 test files were executed directly (not just read) against a live Python 3.12 environment:
test_ai_service.py — 3/3 pass (orchestration success, rate-limited, cache-hit paths).
test_prompt_builder.py — 3/3 pass (label resolution, affects_ai_preview exclusion, sanitizer).
test_compliance.py — 2/2 pass (admin auth incl. bypass/loose-token rejection, filtering).
test_flask_success.py — 1/1 pass (end-to-end POST /api/ai/generate-preview).
test_user_routes.py — 4/4 pass (401/403/200 ownership + admin-override paths).
13/13 tests pass. However, as noted in Finding #2, three of the five test files instantiate the full Flask app via create_app() in setUp(), which attempts a real MongoDB connection for index creation on every single test method. With no local MongoDB running, each instantiation stalls for roughly 20-30 seconds before failing open with a warning. This does not fail the tests, but it makes the suite painfully slow (multiple minutes total) and would likely cause CI timeouts unless a MongoDB service container is provisioned or the app factory is adjusted to skip index creation in a testing config.
8. Recommendations Before Merge
Fix upload_to_cloudinary() to distinguish "no credentials configured" (fine to mock in dev) from "upload call raised an exception" (should propagate as a failure, not a fake success). A generation should never be logged status: "success" with a URL that doesn't point to a real uploaded asset.
Add a testing config (e.g. TESTING=True short-circuits create_indexes(), or use mongomock) so the suite runs in seconds and doesn't depend on a live database.
Confirm with the Module 1 (Auth) lead when the real JWT middleware will replace the X-User-Id header trust, and track it so it isn't forgotten.
Confirm the ownership split for PUT /api/admin/categories/:id/ai-prompt-template with the Module 2 lead in writing, per the spec's own note.
Flesh out README.md with setup steps and the full env var list — currently just the module name.
9. Conclusion
This is a well-structured, spec-literate implementation — the intern clearly read Sections 1-12 closely rather than guessing at a generic AI-wrapper API, and the trickier rules (cache bypass on custom_text, excluding cache hits from rate limits, never leaking provider errors) are all correctly handled. At an estimated 84% completion, the remaining work is concentrated in one real bug (the Cloudinary silent-fallback issue), one already-flagged security placeholder, and test/DX hardening — none of which require architectural rework. Recommended: address Finding #1 (High) before this touches a real order flow, then merge.
